## KPI (질문 정확도 아님)

| # | KPI | Founder 문장 |
|---|-----|--------------|
| 1 | Review Value | 내 사업에서 이것이 문제였구나 |
| 2 | Progress Clarity | 내 사업이 지금 어디까지 검토됐는지 알겠다 |
| 3 | Actionability | 다음에 무엇을 검증해야 하는지 알겠다 |
| 4 | Trust | AI가 내 사업을 제대로 이해하고 있다 |
| 5 | Effort | 계속 답변하는 것이 귀찮지 않다 |
| 6 | Decision Value | 이 결과로 실제 의사결정을 할 수 있다 |

진행률은 `질문 n / 10`이 아니다.

```text
사업 이해       ✓
고객 문제       ✓
시장/대안       진행 중
지불 의사       미검증
사업성 판단     진행 중
```

또는: **지금까지 확인한 것 N개 · 아직 중요한 것 M개.**

## 1. Journey A / B / C

### A. 현재형 — 질문 → 답변 → 질문

Production `1394a8d`가 이것이다. Confirm Yes 후에도 원문 반복, n번째 질문이 진행률, 판단 없음.

### B. 검토형 — 구조화 → 판단 → 리스크 → (질문 없음 또는 나중)

한 장으로 검토 느낌을 준다. 빈칸을 Founder가 고치지 못하면 판단이 틀린 채 고정된다.

### C. Hybrid — 구조화 → 판단 → 핵심 질문 1개 → 답변 → 판단 업데이트

CPO 루프 ①–⑧. 질문은 판단을 바꾸는 빈칸일 때만.

| | A 현재형 | B 검토형 | C Hybrid |
|-|----------|----------|----------|
| Review Value | 낮음. “그래서 검토가 뭐지?” | 첫 장에서 약점을 봄 | 첫 장 + 답변 후 판단이 바뀜 |
| Progress Clarity | 질문 횟수 | 테마 ✓/미검증 | 테마 ✓/미검증 + 방금 바뀐 판단 |
| Actionability | 다음 gap | 리스크는 보이나 다음 행동이 약함 | 리스크 → 질문 1개 |
| Trust | 원문 재출력로 깎임 | 구조화가 원문과 분리되면 상승 | 같음 + 답이 판단에 보임 |
| Effort | 같은 원문 두 번 확인 후 문서에 있는 고객을 다시 씀 | 읽기만 | 읽기 + 가치 있는 질문 1개 |
| Decision Value | 없음 | 초안 판단은 있음 | 판단이 갱신되며 의사결정에 근접 |
| 원문 재출력 | Production에서 확인됨 | 구조화 규칙으로 차단 가능 | 같음 |
| 기존 V3 | 제품의 중심 | 거의 안 씀 → 엔진 낭비 | 하부: gap / next Q only |
| 구현 위험 | 이미 존재 | 질문 수단이 없어 교정 불가 | 새 Review 레이어 + 기존 Question Engine |

**Paper-test 질문:** “이 화면 하나만 봐도 Founder가 사업 검토를 받고 있다고 느끼는가?”

## 4. 예상 SoT / UI

새 레이어 **Founder Review Experience** (제품의 중심).

```text
Founder Review Experience
        ↑
판단 / 리스크 / 진행감
        ↑
┌───────────┴───────────┐
│                       │
Review Engine      Question Engine (P0-1/P0-2)
구조화 / 판단            gapState / next Q
```

필요 (아직 구현 안 함):

- `ReviewState`: 구조화 슬롯 (사업/고객/구매자/문제) — **원문 문자열이 아님**
- `CurrentJudgment` + `KeyUncertainty` — 질문보다 위에 필수
- `ValidationProgress`: 테마 상태 (확인됨 / 진행 중 / 미검증). 질문 카운트 아님
- 게이트: judgment + uncertainty 없으면 next Q 렌더 금지
- Confirm copy `제가 이해한 사업은 「원문」입니다. 맞나요?`를 1차 표면에서 제거
- 기존 `gapState` / `lastDecision` / `decideNextQuestionFromReview`는 ④⑤의 후보 선택에만 사용

만지지 않음: Auth, DB 스키마 전면, P0-1/P0-2 계약, Stage ③/④, PDF, CEO test.

## 5. 기존 V3를 하부 엔진으로 쓸 수 있는가

**Yes — 제품 중심만 옮긴다.**

| 유지 | 역할 변경 |
|------|-----------|
| `buildAnswerReview` → `gapState` | 답 반영 SoT |
| CLOSED 단조성 | 슬롯이 되살아나지 않음 |
| `decideNextQuestionFromReview` | 판단-변경 빈칸의 **후보** |
| Confirm Yes → 엉뚱한 슬롯 금지 (P0-1) | Review 레이어 아래에서도 유효 |

| 더 이상 UI SoT가 아님 | 이유 |
|----------------------|------|
| `lastDecision.questionText`만으로 화면 구성 | 판단/리스크 없이 질문이 올라옴 |
| `질문 n번째` | 진행률이 아님 |
| 원문 클립을 understanding / 기존 답변으로 표시 | Trust·Review Value 파괴 |

Question Engine이 고장 나서가 아니다. **그 엔진을 제품 중심에 둔 전략이 틀린 것**이다.

## 6. 최종 추천

**Journey C — Hybrid Review-Centric.**

이유:

1. Production A는 B–F = NO, Decision Value 없음.
2. Paper Test 5개에서 C만 “이 화면이 검토다”에 YES.
3. B는 교정 루프가 없어 틀린 판단이 고정됨.
4. V3를 버리지 않고 하부로 둘 수 있다.

Strategy Gate 다음 구현이 열려도, 첫 코드는 질문 문구/버튼이 아니라 **판단+리스크 없이 질문을 렌더하지 않는 Review 표면**이어야 한다.

CEO 테스트는 “버튼이 눌리는가”가 아니라 **“이 제품이 내 사업을 검토해 주는가”**일 때 연다.
