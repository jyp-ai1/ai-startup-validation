이 파일은 조사와 설계다. 제품 코드와 테스트는 바꾸지 않았다. 구현 승인은 없다.

Production 잠금 SHA: 0b465226
브라우저 세 시나리오는 이전 기록 그대로 미검증이다. 이 문서의 엔진 설명으로 화면 일치를 대신하지 않는다.

1. 실제 런타임 경로

워크스페이스가 렌더될 때 순수 엔진 si-judgment-contract.ts 는 호출되지 않는다. apps 아래에서 그 파일을 import 하는 곳은 테스트 두 개뿐이다. 동적 import 도 없다.

경로 가. 화면에 올라가는 S.I. 문장과 질문.

Founder 가 WorkspaceDocumentIntake 에 글을 넣으면 v2-strategy-workspace.tsx 의 handleDocumentIntake 가 받는다. 입력 타입은 string 이다. 데모 안내 모드에서는 saveWorkspaceDocumentText 가 그 문자열을 저장한다. 그 외에는 도메인 추론 후 기존 persistWorkspaceStateDbFirst 를 호출한다. 이번 설계는 그 저장을 바꾸지 않는다.

WorkspaceAiPmMain 은 loadWorkspaceDocumentText 또는 buildDocumentContext 결과를 siInputText 로 둔다. 길이가 8 미만이거나 documentAnalyzable 이 아니면 siJourney 는 null 이다.

문서가 있으면 useMemo 가 resolveSiJourneyIntegration 을 호출한다.
파일: apps/web/features/workflow-journey/components/project-workspace-shell/workspace-ai-pm-main.tsx
입력: SiJourneyIntegrationInput. title, businessDocument, founderAnswer, gapLoopDocument.
반환: SiJourneyIntegrationResult. firstJudgment, firstQuestion, current.

그 함수 본문은 resolveSiAiPmBindView 를 두 번 호출한다.
파일: apps/web/features/strategic-intelligence/lib/resolve-si-journey-integration.ts
입력: documentText, title, founderAnswer.
반환: SiAiPmBindView. judgment 는 SiStrategicJudgment, question 은 SiAiPmQuestion.

resolveSiAiPmBindView 본문:
- analyzeStrategicIntelligence({ title, documentText }) → SiStrategicJudgment
- decideSiValidationAsk(previous) → SiValidationAsk
- presentSiAiPmQuestion(ask, { documentText }) → SiAiPmQuestion
founderAnswer 가 비어 있으면 updateStrategicIntelligence 를 호출하지 않고 previous 를 반환한다.

워크스페이스의 setSiFounderAnswer 호출은 두 곳 모두 null 이다. 프로젝트 변경 때와 답변 제출 때다. 따라서 현재 화면 런타임은 founderAnswer 를 비운 채로만 resolveSiJourneyIntegration 에 들어간다. updateStrategicIntelligence 는 이 호출 경로에 없다. 답변은 recordSiMatchedAnswerOnLoop 로 루프 저장소에만 남고, resolveSiMatchedAnswerStorage 는 appendDocument false 를 반환한다. 주석과 구현이 같다. 답변 문장을 S.I. 문서에 붙이지 않고 analyzeStrategicIntelligence 를 다시 호출하지 않는다.

렌더. isPostReview 가 아니면 SiReviewSurface 가 judgment.judgment 를 그린다. SiAiPmBindSurface 가 question.questionText 와 question.whyAsking 을 그린다. isPostReview 는 reviewCount >= 1 또는 리뷰 완료 또는 결과 요청이다. 그 이후 S.I. 블록은 렌더되지 않는다.

경로 나. 루프가 고르는 다음 질문. 경로 가와 동시에 있다.

WorkspaceAiPmLoopPanel 이 siValidationAsk 로 경로 가의 SiAiPmQuestion 을 받는다. siTurnInsightFromQuestion 은 kind 를 gap id 목록으로 바꾼다. analyzeStrategicIntelligence 를 다시 호출하지 않는다. selectNextAction 도 호출하지 않는다.

resolveNextQuestionDecision 은 living, turns, memory, gapState, ceoJudgment 로 다음 질문을 고른다. siInsight 는 decideNextQuestionFromReview 를 거쳐 scoreCandidate 에서 선호 gap 에 800 을 더한다. 질문 문장의 출처는 이 결정이다.

그 다음, siValidationAsk 가 있고 preferredGapIds 가 그 targetGap 을 포함하고 확인 질문이 아니면, 화면 문장만 siValidationAsk.questionText 로 덮어쓴다. 선택을 순수 엔진이 한 것이 아니다.

판단 문장의 또 다른 출처는 loopState.ceoJudgment 다. buildCeoJudgmentState 가 oneLiner, conclusion, nextCheck 를 만든다. WorkspaceAiPmJudgmentView 가 그 문자열을 그린다. 이 함수도 순수 엔진을 호출하지 않는다.

순수 엔진 경로. 테스트만 호출한다.

createProjectLedger 또는 createSeedLedger → JudgmentLedger
applyFounderAnswer, bindLiteralFact, resolveConflict, defineCriterion 가 이벤트를 적용하고 reassess 가 한 상태를 다시 계산한다.
selectNextAction(ledger) → DecisionRecord. prompt 가 다음 행동 문장이다.
이 반환값은 워크스페이스 props 로 전달되지 않는다.

2. 계약 비교

분류는 워크스페이스 런타임 기준이다.

판단 문장. 3. 화면은 SiStrategicJudgment.judgment 또는 CeoJudgmentState.oneLiner 와 conclusion 을 쓴다. 순수 엔진의 JudgmentLedger.judgment 는 이 경로에 없다.
다음 행동. 3. 화면은 presentSiAiPmQuestion 의 questionText, 또는 resolveNextQuestionDecision 의 questionText 다. 조건이 맞으면 전자가 후자의 문장만 덮는다. DecisionRecord.prompt 는 이 경로에 없다.
활성 가설과 역할. 4. HypothesisRole 과 hypotheses 는 화면 타입에 없다. 순수 엔진 런타임 호출이 없으므로 계산되지도 않는다.
outcome. 4. ValidationOutcome 은 JudgmentLedger.hypotheses 에만 있다. SiStrategicJudgment 와 CeoJudgmentState 에는 없다.
근거 귀속과 충돌. 3 과 4 를 나눈다. 화면의 evidenceMap.evidenceClass 는 문서 스캐너가 CONFLICT 를 붙일 수 있다. 그것은 별도 로직이다. ProjectAttribution 과 UnresolvedConflict 는 순수 엔진에만 있고 화면 경로에는 없다.
validationPlan.status. 4. ValidationPlan 은 JudgmentLedger 에만 있다. 화면 타입에 없다.
reviewCompletion. 4. JudgmentLedger.reviewCompletion 만 있다. 화면 타입에 없다.

따라서 1 에 해당하는 항목은 없다. 2 에 해당하는 항목도 없다. 순수 엔진이 워크스페이스 요청 안에서 계산된 뒤 버려지는 구조가 아니다. 호출 자체가 없다.

3. 세 시나리오

화면 결과는 미검증을 유지한다. Preview SSO 로 제품 화면에 들어가지 못했다.

A. 고객 변경.
화면 재현: 현재 구조로는 순수 엔진의 고객 교체를 화면에 재현할 수 없다. 입력은 루프 답변으로 저장되고 S.I. 문서는 바뀌지 않는다. 화면 질문 엔진은 gap 이다.
순수 엔진: 결정론적으로 재현된다. replace 가 이전 고객을 conflict-side 로 두고 이전 문제를 inactive-preserved 로 두며, 다음 질문은 새 고객의 빈 문제다. 기존 테스트가 그 상태를 고정한다.
동일 입력 비교: 불가. 화면 상태와 JudgmentLedger 가 같은 객체가 아니다.
최소 연결: 고객 교체 이벤트를 applyFounderAnswer 의 replace 로 넣고, 화면 문장은 그 ledger.judgment, 다음 행동은 그 selectNextAction().prompt 만 읽는다.

B. 고객 충돌 해소.
화면 재현: 불가. 화면은 resolveConflict 를 호출하지 않는다. e2e 의 resolveConflictIfShown 은 다른 대화 화면 보조 함수다.
순수 엔진: 결정론적으로 재현된다. 고객 충돌이 핵심이면 해소 후보가 지불자 질문보다 앞선다. 해소 후 고객 outcome 은 passed 가 아니고 VALIDATED binding 을 만들지 않는다.
동일 입력 비교: 불가.
최소 연결: 사용자가 고른 근거 id 로 resolveConflict 를 호출한 뒤 같은 ledger 에서 문장과 다음 행동을 읽는다. 선택 이유에 passed 또는 VALIDATED 를 쓰지 않는다.

C. 문자 기록 선택.
화면 재현: 불가. bindLiteralFact 와 validationPlan 이 화면 경로에 없다.
순수 엔진: 결정론적으로 재현된다. 문자 FACT 를 작업 기준으로 고르면 귀속은 unreviewed, 사업모델 outcome 은 insufficient_record, 계획은 proposed 다. 엔진은 executed 를 쓰지 않는다.
동일 입력 비교: 불가.
최소 연결: bindLiteralFact 다음 resolveConflict 의 ledger.validationPlan.status 와 귀속, outcome 을 화면용 문장으로만 투영한다.

4. 최소 통합 설계. 구현하지 않음.

단일 출처는 JudgmentLedger 하나다. analyzeStrategicIntelligence 의 SiStrategicJudgment 와 CeoJudgmentState 는 이 세 시나리오의 판단 문장과 다음 행동의 출처가 아니다.

재계산 시점: FounderAnswerAct, bindLiteralFact, resolveConflict 가 적용된 직후 reassess 가 이미 하는 그 한 번이다. 화면은 그 결과를 다시 해석해 두 번째 판단을 만들지 않는다.

UI 가 읽을 최소 공개 타입. 가칭 WorkspaceJudgmentView.
- judgmentSentence: ledger.judgment
- whyPossible, whyFail, criticalUnknown, decisionChangingEvidence: ledger 의 같은 필드
- nextActionSentence: DecisionRecord.prompt
- planSentence: validationPlan.status 가 proposed 일 때만 evidenceNeeded 와 pendingWork 를 문장으로. not_required 이면 계획 문장을 비운다. executed 는 만들지 않는다.
- attributionSentence: unreviewed, accepted, rejected 를 사용자 문장으로. 내부 열거 이름을 그대로 노출하지 않는다.
이 타입에는 hypothesis id, uncertainty id, targetGap, score, tieBreak, candidate id 를 넣지 않는다.

다음 행동 경로: selectNextAction(ledger).prompt 를 nextActionSentence 로 둔다. presentSiAiPmQuestion 과 resolveNextQuestionDecision 은 이 문장을 덮지 않는다.

중복 제거: 세 시나리오가 보이는 동안 SiReviewSurface 와 SiAiPmBindSurface 와 루프 질문과 CEO 판단 뷰가 서로 다른 문장을 동시에 보여주지 않는다. 보이는 판단 문장과 다음 행동은 WorkspaceJudgmentView 하나다. 문서 스캐너와 gap 랭킹은 그 뷰의 입력이 아니다. 함수 자체는 다른 화면이 쓰면 당장 삭제하지 않는다. 이 뷰의 출처에서만 뺀다.

기존 저장소에 장을 추가하는 것은 이번 최소안의 전제가 아니다. 세션 안의 ledger 로 먼저 비교할 수 있다. 새 테이블, 새 모델, 새 호스팅은 전제가 아니다.

자유 입력을 이벤트로 바꾸는 경계: 이미 있는 FounderAnswerAct 와 resolveConflict, bindLiteralFact 만 쓴다. 문장을 분류할 수 없으면 엔진에 추측 이벤트를 넣지 않고, 다음 행동은 현재 ledger 의 prompt 를 유지한다. 모델 호출로 분류하지 않는다.

5. 승인 후 바꿀 파일. 지금은 바꾸지 않음.

- 새 파일. strategic-intelligence/lib 의 순수 표시 함수. ledger 와 DecisionRecord 를 WorkspaceJudgmentView 로 바꾼다. 판단 로직을 복제하지 않는다.
- workspace-ai-pm-main.tsx. 세 시나리오의 표시 출처를 그 뷰로 바꾼다.
- workspace-ai-pm-loop-panel.tsx 의 질문 문장 덮어쓰기. 엔진 prompt 가 있을 때 gap 문장으로 바꾸지 않는다.
- 표시 테스트. 아래 6.

바꾸지 않을 파일: si-judgment-contract.ts 의 전이 규칙, DB 마이그레이션, provider, 인증, Preview 설정.

위험: 표시 함수가 문장을 다시 쓰면 두 번째 판단이 된다. 고객 교체를 자유 텍스트에서 잘못 고르면 이전 문제가 빠진다. 루프와 S.I. 블록을 동시에 두면 불일치가 화면에 남는다. isPostReview 가 S.I. 블록을 숨기므로, 연결 후에도 그 조건에서 뷰가 빠지면 화면은 다시 루프만 보인다.

6. 통합 회귀 계획. 실행하지 않음. 승인 후.

기존 43개와 30행 재생은 그대로 둔다. 기대값을 화면에 맞추기 위해 바꾸지 않는다.

추가할 테스트는 표시 함수와 호출 경계다.
- 같은 ledger 와 같은 DecisionRecord 를 두 번 넣으면 같은 WorkspaceJudgmentView 다.
- 고객 변경 엔진 결과의 judgmentSentence 와 nextActionSentence 가 ledger.judgment 와 prompt 와 같다. 뷰 문자열에 h-problem, targetGap, score 가 없다.
- 충돌 해소 결과의 뷰가 passed 와 VALIDATED 를 사업 성공 문장으로 쓰지 않는다.
- 문자 기록 선택의 뷰가 unreviewed 와 insufficient_record 의 의미를 유지하고, planSentence 가 proposed 의 evidenceNeeded 와 같고 executed 를 말하지 않는다.
- 워크스페이스가 이 뷰를 읽는 호출이 analyzeStrategicIntelligence 와 decideSiValidationAsk 의 반환으로 판단 문장과 다음 행동을 다시 만들지 않는지. 이 단언은 연결 구현 후에만 추가한다. 지금은 그 호출이 없으므로 실패로 단언하지 않는다.

이 테스트가 통과해도 브라우저 검증은 아니다. Preview 에서 같은 문장을 읽기 전에는 세 시나리오를 미검증으로 둔다.

7. 미검증과 별도 승인

- 제품 화면의 판단 문장과 다음 행동. Preview SSO. 미검증.
- 화면과 엔진의 일치와 불일치. 선언하지 않음.
- 이 설계의 구현. 승인 전.
- 자유 입력에서 replace, resolveConflict, bindLiteralFact 를 고르는 규칙의 구체 문장. 구현 범위에 넣기 전에 한 번 더 확정할 항목이다.
