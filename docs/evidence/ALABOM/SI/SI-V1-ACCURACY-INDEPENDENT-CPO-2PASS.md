## 1. 지불만으로 S3 — 6개 사업

**실패 유형:** `over_promote_on_partial`  
**재현:** 미등록 지표 6 / 6. 대조군 0 / 2.

### 원인 (수정 없이 경로만)

1. `quantified_problem`은 `%` + `STAKE_NOUN`일 때만 켜진다 (L296–301).
2. `dceStakeOpen` = `quantified_problem && !stake_improved` (L607–609). 미등록 지표는 항상 false.
3. `decideStage`: 매출이 있고 `dceStakeOpen`이 아니면 **S3** (L622–624).
4. `decideVerdict`: `dceStakeOpen`이면 보류. 아니면 매출이 있으면 조건부/가능 (L655–660).

지불 한 번이 사업성 검증을 대체한다. 허용 목록을 늘리면 목록 밖 다음 지표에서 같은 경로가 다시 열린다.

### 대조군 — 임상 피험자 모집 (노쇼)

입력 문서:

```
국내 CRO는 병원 게시판으로 피험자를 모아 스크리닝 방문 노쇼가 31%입니다.
기존 대안은 병원 게시판과 간호사 전화 독촉입니다.
아직 출시되지 않았고 매출은 없습니다.
결제자는 CRO 프로젝트 매니저입니다.
```

답: `CRO 2곳이 월 구독을 결제했다.`

| | 최초 | 지불만 이후 |
|---|---|---|
| 판정 | `judgment_deferred` / S0 | **`judgment_deferred` / S0** |
| 판단 | 지금은 판단을 보류한다. … 노쇼 수치가 실제로 줄어드는가 | 유료 전환 이후 … 노쇼 수치가 실제로 줄었는가 |
| 질문 | 노쇼 수치를 실제로 얼마나 줄였고 … | 동일 축 (paid_conversion) |
| 증거 | — | VALIDATED (지불 수량) |

#104와 같은 동작: 지불만 ≠ S3.

### 실패 예 — 냉동물류 IoT (온도 초과)

입력 문서:

```
수도권 냉동탑차 30대를 운용하는 3PL은 종이 온도기록지로 관리해서 하절기 온도 초과가 주 14건입니다.
기존 대안은 종이 온도기록지와 기사 수기 보고입니다.
아직 출시되지 않았고 매출은 없습니다.
결제자는 물류사 운영팀장입니다.
```

답: `물류사 2곳이 월 구독을 결제했다.`

| | 최초 | 지불만 이후 |
|---|---|---|
| 판정 | `judgment_deferred` / S0 | **`conditionally_viable` / S3** |
| 판단 | 가치가 실제 지불로 이어지는가 | 조건부 사업화 가능. 반복 가능한 사업으로 이어지는가 |
| CU | 일반 유료 전환 (온도 초과 없음) | 반복 루프 (온도 초과 없음) |
| 질문 | 유료로 제안했거나 받은 돈이 있습니까 | 두 번째 행동이나 반복 사용이 있습니까 |
| 증거 | — | VALIDATED |

같은 패턴이 치과기공·굴착기·급유·3D수탁·급식 잔반에서 재현. 입력·출력 전문은 JSON `classes.payment_only_s3.failing`.

## 2. 부정 지표 악화 미반영 — 6개 사업

**실패 유형:** `missed_downgrade`  
**재현:** 미등록 지표 6 / 6. 대조군 0 / 2 (CONFLICT → 보류).

### 원인

`isStakeWorsenedLine`이 `STAKE_NOUN`을 요구한다 (L103–108).  
`온도 초과가 4건에서 13건으로 늘었다`는 악화로 인식되지 않는다.  
`노쇼가 12%에서 29%로 늘었다`는 CONFLICT로 내린다.

### 대조군 — 소상공인 해외송금 (불일치)

선행 답(full): `수출 대표 3명이 송금 수수료를 결제했고 불일치가 16%에서 5%로 줄었다.` → 조건부 / S3  
악화 답: `다음 기간에 불일치가 5%에서 15%로 늘었다.`

이후: **`judgment_deferred` / S0**, 증거 **CONFLICT**, CU가 다시 `불일치` 전후.

### 실패 예 — 냉동물류 IoT

선행 full: `물류사 2곳이 월 구독을 결제했고 온도 초과가 주 14건에서 4건으로 줄었다.` → 조건부 / S3  
악화 답: `다음 주에 온도 초과가 4건에서 13건으로 늘었다.`

이후: **그대로 `conditionally_viable` / S3**, 증거 FACT, CU는 일반 반복 루프. 악화가 판단에 없다.

## 3. C2C 재판매 답 → S4 — 8개 사업

**실패 유형:** 승격은 `axis_drift` 경로. 헤드라인은 `leftover_positive`.  
**재현:** **8 / 8** (허용 목록 사업 포함).

공통 답(사업과 무관):

```
최근 구매자 100명 중 35명이 실제 재판매를 등록했고 12건이 거래됐다.
```

### 원인

`hasCountedCompletion`은 `등록했|거래됐|재구매했|실제로 재판매` + 수량이면 true (`quantity-unit.ts` L17, L90–95).  
analyzer는 이를 `repeat_validation` VALIDATED로 올린다 (L267–268).  
`decideStage`: repeat_validation → **S4** (L621).  
`decideVerdict`: `hasRepeat && hasRevenue` → **viable** (L654).  
답의 축이 현재 CU(다음 기간 / 일반 반복)와 달라도 막지 않는다. `C2C|재판매`는 `resale_thesis`를 켜지만, 이미 VALIDATED repeat가 있으면 보류하지 않는다.

### 출력 (8개 동일 구조)

full 이후: `conditionally_viable` / S3  
재판매 답 이후: **`viable` / S4**

냉동물류 판단 문장:

```
현재 판단: 사업화 가능성이 높음. 핵심 근거: 실제 판매·매출 증거가 있다. 핵심 리스크: 출시·매출 등 상업 실행 증거가 없다.
```

CU는 다시 일반 반복. 질문은 두 번째 행동. 냉동 온도 초과는 어디에도 없다.

## 5. 헤드라인 · 근거 · CU 충돌 — 8개 사업 × 2장면

**실패 유형:** `leftover_positive`  
**재현:** wrong_axis 8 + closed_reask 8.

### 원인

원문 `아직 출시되지 않았고 매출은 없습니다`가 `no_launch` / `no_revenue` FACT로 남는다 (L252–260).  
이후 지불이 VALIDATED여도 `buildRisks`는 `출시·매출 등 상업 실행 증거가 없다`를 그대로 넣는다 (L852–854).  
`proseJudgment` viable 템플릿은 strengths[0](`실제 판매·매출 증거가 있다`)과 risks[0](위 문장)을 한 줄에 붙인다 (L887–890).

CPO가 볼 충돌:

- 헤드라인: 사업화 가능성이 높음  
- 근거: 실제 판매·매출 증거가 있다  
- 리스크: 출시·매출 등 상업 실행 증거가 없다  
- CU: 반복 가능 여부 (해당 사업 지표 없음)

## 일반화 규칙 (구현 아님 · CPO 판정용)

허용 목록을 늘리는 것은 다음 미등록 명사에서 1–2–4를 재현한다. 사업명 하드코딩도 동일.

CPO가 Fix Gate를 열면 그때만 아래를 일반 규칙으로 구현한다.

1. 문서가 수치화한 핵심 지표는 닫힌 한국어 명사 목록이 아니라, 수량·악화/개선 동사·문서 내 지표 표현으로 연다.
2. 그 지표가 안 움직이면 지불만으로 S3/조건부 승격을 막는다 (`dceStakeOpen`과 동등한 일반 조건).
3. 같은 지표의 악화는 하향(또는 CONFLICT)이다.
4. 완료/재판매 수량은 **현재 CU 축과 맞을 때만** repeat_validation이 된다.
5. 나중 VALIDATED 매출이 있으면 `no_revenue` 리스크를 헤드라인에 남기지 않는다.
