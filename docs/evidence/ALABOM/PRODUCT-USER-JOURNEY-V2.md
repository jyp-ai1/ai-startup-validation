# Product User Journey V2

**Status:** DESIGN ONLY — CPO review. No code.  
**Companion:** `PRODUCT-IA-V2.md` · `PRODUCT-STATE-MODEL-V2.md` · `PRODUCT-UX-WIREFRAME-V2.md`

이 문서는 Founder가 **입력 → 확인 → 검증 → 판단 → 보고서**까지 한 줄로 걷는 길이다.  
CEO Production 양조장 사례를 설계 검증에 쓴다. 값을 엔진 정답으로 하드코딩하지 않는다.

---

## 1. 북극성 여정

```text
사업 입력
  ↓
AI Interpretation   「AI가 이해한 내용」
  ↓
사용자 확인/수정     CONFIRMED
  ↓
① 사업 정의         Canonical gap을 닫음
  ↓
② 시장 검증
  ↓
③ 사업성 검토
  ↓
④ 사업성 판단
  ↓
보고서              Project Context 렌즈
```

AI가 리드한다. Founder는 다음 메뉴를 고르지 않는다.

---

## 2. 화면이 아니라 상태의 여정

각 순간 Founder가 답할 수 있어야 하는 여섯 질문:

| # | 질문 | 어디서 답하는가 |
| --- | --- | --- |
| 1 | 어디까지 왔는가 | Left Stage |
| 2 | 왜 아직 다음이 아닌가 | Right 미확인 Canonical |
| 3 | AI가 무엇을 이해했는가 | Center `AI가 이해한 내용` |
| 4 | AI가 무엇을 추측했는가 | 가정 라벨 |
| 5 | 내가 지금 확인할 것은 | Center 현재 질문 또는 첫 확인 |
| 6 | 무엇이 아직 모름인가 | Right ○ |

## 3. 단계별 Founder 경험

### 3.1 프로젝트 생성

입력:

```text
Project Title     사용자가 지은 이름
Business Source   사업내용 전체 (3~4줄이어도 잘리지 않음)
Project Context   사용 목적 (질문 스택이 아님)
reviewType        무엇을 검토하는가 (기존 필드, 유지)
```

직후:

- Title이 헤더에 보인다.
- Source는 `[전체 사업내용 보기]`.
- Left: ① ● / ②③④ ○
- 「사업 정의 ✓」가 되면 이 여정은 실패한 것이다.

### 3.2 AI가 이해한 내용 (한 번만)

Center에 카드 **하나**:

```text
AI가 이해한 내용
<Interpretation — Source 복붙 금지>
근거  사업내용에서 확인 | 추론

[맞습니다]   [이해 수정하기]
```

- 맞습니다 → Interpretation의 명시된 칸이 CONFIRMED. 카드는 사라지고 첫 unresolved Canonical 질문.
- 이해 수정하기 → AI가 채운 슬롯을 고친다. 빈 폼 재작성 금지.

같은 확인 카드가 다음 화면에 다시 나오면 여정이 깨진 것이다.

### 3.3 확인 루프 (반복 단위)

```text
다음 unresolved Canonical gap
  ↓
질문 하나
  ↓
답변
  ↓
Knowledge 갱신 (FACT / 가정 / 모름 / 충돌)
  ↓
Right 상태 변화 (사용자는 왜 질문이 바뀌었는지 봄)
  ↓
다음 unresolved
```

한 화면에 질문 하나.  
사업/고객/시장/경쟁을 한 번에 묻지 않는다.

### 3.4 충돌

이전 CONFIRMED와 새 답변이 다르면:

```text
이전 확인: …
새 답변: …

[새 답변이 맞아요]  [이전 확인이 맞아요]
```

선택 후 해당 gap은 하나의 Confirmed만 남긴다. 같은 확인 카드로 돌아가지 않는다.

### 3.5 Stage가 넘어갈 때

Right가 `4/4 확인`이 되고 V3 `stageAReady`가 참이면:

```text
사업 정의가 충분합니다. 이제 시장을 확인합니다.
```

Left ① ✓, ② ●.  
답변 개수가 이유가 되면 안 된다.

### 3.6 결과 · 보고서

```text
현재 판단
확인된 사실
AI의 가정
미확인 사항
핵심 리스크
다음 검증
[보고서]
```

Context 렌즈:

| Context | 결과에서 먼저 보이는 것 |
| --- | --- |
| 창업자 / 예비창업자 | 다음 검증, 실행 가능성 |
| 전략기획 | 시장·경쟁·차별 |
| 투자검토 | 리스크, 경제성, HOLD 이유 |
| 시장조사 | 수요 근거, 검증 설계 |

모든 렌즈가 같은 Confirmed Knowledge를 읽는다. 다른 판단을 날조하지 않는다.

## 4. CEO 사례 — 양조장 (설계 walkthrough)

### 4.1 Input (Source)

```text
Project Title
양조장 체험 관광 서비스          ← 사용자가 입력한 이름. 없으면 "이름 없는 프로젝트"

Business Source
다양한 관광객이 늘며, 개인별 다양한 경험을 중요시 한다.
전통주와 양조장 체험을 좋아하는 내국인과 외국인을 대상으로
양조장 체험과 주변 관광 경험을 제공하려 한다.
```

헤더에 Source 앞부분을 제목으로 올리면 **FAIL**.

### 4.2 AI Interpretation (예시 — 정답 하드코딩 아님)

중요한 것은 문장 형태가 Source가 아니라는 점이다.

```text
AI가 이해한 내용

전통주·양조장 체험을 원하는 내국인 및 외국인 관광객에게
양조장 체험과 주변 관광을 연결하는 서비스로 이해했습니다.

근거  사업내용에서 확인
```

슬롯 초안 (추출, 아직 전부 CONFIRMED 아님):

```text
사업    전통주/양조장 체험 관광 서비스          제안
고객    전통주/양조장을 좋아하는 내국인·외국인 관광객  제안
시장    개인화 관광 / 미식·전통주 관광           추측
경쟁    기존 전통주 소개·판매·체험 서비스         추측
문제    아직 모름                               ○
구매자  아직 모름                               ○
```

### 4.3 확인 후 Right (입력만으로는 ① 미완료)

```text
현재 검증 상태

사업       △     AI 제안 · 확인 필요
고객       △     AI 제안 · 확인 필요
핵심 문제  ○
구매자     ○
시장/채널  ○
대안/경쟁  ○

2/4 부분 제안 · 사업 정의 0/4 확인
현재 단계  ① 사업 정의
판단 가능 여부  아직 판단하기 어려움
```

「사업이해 ✓」면 **FAIL**.

### 4.4 사용자가 맞습니다 → 첫 질문

Interpretation 확인은 **서술 동의**다. Canonical 4칸을 자동 CLOSED 하지 않는다.  
(문서에서 읽힌 사업/고객은 △ 또는 문서근거 제안. Founder가 칸을 확인하거나 답변으로 닫는다.)

첫 질문은 가장 비싼 unresolved Canonical — 대개 고객 또는 구매자/문제.

```text
지금 확인할 것 · 고객과 구매자

체험하는 사람과 돈을 내는 사람이 같습니까?

[답변]
```

### 4.5 답변 후 사용자가 보는 변화

답변: `사용자는 관광객이고 구매자는 양조장 대표가 결제합니다.`

```text
RIGHT
고객    △→ 관광객 (확인 중/확인)
구매자  ○→ ✓ 양조장 대표

CENTER
기존 답변 …  [답변 수정하기]
다음 질문 (문제 또는 사용 맥락의 Canonical)
```

Summary가 그대로면 여정이 죽은 것이다.

### 4.6 수정 · Conflict

수정: 고객을 `예비 관광객과 현지 여행객`으로 정정 → 같은 슬롯 갱신.  
Conflict: `관광객이 앱에서 직접 예약·결제` vs `양조장 대표 결제` → 한 쪽만 CONFIRMED.

이후 3번째 질문. 확인 카드로 리셋되지 않음.

### 4.7 결과로 가는 조건

① 4 Canonical ✓ → ② → (표시상 ③) → 판단 산출물.  
중간에 결과 CTA를 눌러도 Right는 `아직 판단하기 어려움`을 숨기지 않는다.

결과 최소 구성 (양조장 예시 뼈대):

```text
현재 판단     HOLD 또는 조건부
확인된 사실   고객=관광객, 구매자=양조장 대표 (사용자가 확정한 값)
AI의 가정     시장=미식·전통주 관광 (아직 검증 전)
미확인        핵심 문제, 차별, 검증 방법
핵심 리스크   결제 주체 충돌이 해소됐는지
다음 검증     Context가 창업자면 “대표 1명 인터뷰”, 투자검토면 “지불의사 근거”
```

## 5. 현재 Production 여정 vs V2 (문서화 — 코드 수정 없음)

### 5.1 Confirmation

| | 현재 (PR #79 Production) | 기대 (V2) |
| --- | --- | --- |
| 상태 | `understandingPhase`: pending → accepted. 카드 2개 공존 가능 | `interpretation` → `confirmed` → `asking`. 카드 1개, 전이 후 unmount |
| 이벤트 | 맞습니다 | 맞습니다 / 이해 수정하기 |
| 기대 다음 | 첫 질문만 | 첫 질문만. 이해 카드 제거 |
| 실제 다음 | Center에 이해 블록 + document-first 카드 + composer의 맞습니다가 남을 수 있음 | 같은 confirmation state 재렌더 금지 |

```text
현재 상태     pending + 이중 이해 UI
현재 이벤트   맞습니다
현재 기대     첫 unresolved 질문
현재 실제     같은 확인 CTA가 남아 재클릭 가능
```

이번 Phase는 코드를 고치지 않는다. 구현 Sprint의 첫 전이 계약이다.

### 5.2 Title / Source

| | 현재 | 기대 |
| --- | --- | --- |
| 헤더 | 프로젝트명이 Source 앞줄로 대체되는 사례 | Title 필드만 |
| 이해 슬롯 | 원문 truncation이 사업 칸에 남는 사례 | Interpretation 서술 + 원문 접힘 |

### 5.3 Stage

| | 현재 | 기대 |
| --- | --- | --- |
| 라벨 | 사업이해 / 시장검증 / 사업성검토 / 결과 | ① 사업 정의 / ② 시장 검증 / ③ 사업성 검토 / ④ 결과 |
| 완료 | 이해 화면 진입 후 사업이해가 completed로 합쳐질 수 있음 (`workspace-sidebar` merge) | Canonical 4개 CLOSED 전에는 ①이 ✓가 아님 |

## 6. 사용자가 폼을 쓰지 않는 이유

여정의 마찰은 「빈 칸 20개」가 아니라 「지금 이 한 칸」이다.

- 입력 부담을 Founder에게 전가하면 AI PM이 필요 없다.
- AI가 추출하고 Founder가 틀린 칸만 고치면, 확인된 지식의 밀도가 올라간다.
- 그 밀도만이 사업성 판단의 재료다.

---

## 7. AI PM이 필요한 이유 (여정 관점)

1. Founder는 Source를 이미 썼다. 다시 쓰게 하지 않는다.
2. Source ≠ 이해. 이해 ≠ 확정.
3. 다음 행동은 메뉴가 아니라 **아직 모르는 Canonical 한 칸**이다.
4. 결과는 대화 로그가 아니라 **확인된 사실 / 가정 / 모름**의 보고서다.
